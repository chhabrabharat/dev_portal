# PRD — Staff management and lead ownership (dev_portal)

**Product:** EaseMyOPD (company operations)
**Surface:** `dev_portal` (company-side console)
**Status:** Draft for review. Nothing built.
**Owner:** Company operator (ADMIN)

---

## Why this is in dev_portal

The company selling EaseMyOPD also has its own staff: the people who sell the product, follow up
enquiries and onboard clinics. Today nothing records who those people are, who generated a lead,
or who closed it. The contact-us enquiry inbox from the v1 PRD shows unclaimed enquiries, but not
which company employee worked them.

This module holds **company-internal** data about company employees. It is not clinic data and
does not touch `health`'s tenant-scoped tables for clinic staff.

## Problem

1. No single record per employee: basic details, qualification, designation and documents live in
   scattered files and WhatsApp threads.
2. Staff ID cards and visiting cards are made by hand in a design tool, one at a time.
3. Lead credit is unknown. We cannot say which employee generated a lead or closed it, so
   incentives and performance cannot be judged.
4. Salary and bonus figures have no restricted home. They are shared informally.

## Goals

1. One profile per staff member with basic info, qualification, designation and documents.
2. Print an ID card (with profile photo) and a visiting card from the profile.
3. Record **lead generated by** and **lead closed by** on every sales lead, and report both per person.
4. Salary and bonuses are visible **only** to the ADMIN role, enforced on the server.
5. A first-start ADMIN login, with a one-time password, that can enter details, print cards and see lead credit.

## Non-goals

- **Payroll.** No salary slips, tax, PF, ESI, payment runs or bank transfers. Salary is a stored
  figure and a bonus is a stored amount, nothing more.
- **Attendance, leave, or HR workflow approvals.**
- **Clinic-side users.** Clinic staff logins stay in `health` and `crm_frontend`.
- **Storing Aadhaar numbers.** Consistent with the clinic CRM decision to remove Aadhaar from the
  system, staff profiles do not hold an Aadhaar number. Documents may be uploaded, but the upload
  is stored as a file and never parsed for a number.
- **Commission calculation.** Bonuses are recorded amounts entered by ADMIN. The console does not
  compute them from lead counts in v1.

## Roles

| Role | Staff profiles | Salary and bonus | Print ID / visiting card | Lead credit |
| --- | --- | --- | --- | --- |
| `PLATFORM_ADMIN` (ADMIN) | full read/write | read/write | yes | all |
| `PLATFORM_SUPPORT` | basic info and documents, read only | **hidden** | no | read only |
| `PLATFORM_SALES` | no staff pages | hidden | no | own pipeline leads (write), Pipeline tab only |

The ADMIN role already exists as `PLATFORM_ADMIN`, and the sales role as `PLATFORM_SALES` (Leads and
Pipeline tabs only). v1 adds no new role. Staff profiles are not visible to `PLATFORM_SALES`.

### The seeded ADMIN login

The request is a login `admin` with password `admin`. **Do not ship a hard-coded `admin/admin`
account.** It is the first thing anyone trying this console would try, and it would expose
salary data. Instead:

1. The first start creates `admin` with a **random one-time password** printed once to the server
   log (or set from an environment variable `DEVPORTAL_ADMIN_INITIAL_PASSWORD`).
2. The account is flagged **must change password at first login**. Until it changes, it can only
   reach the password screen.
3. The password is stored hashed, like any other login.

If a fixed `admin/admin` is still wanted for a local demo, it may exist only in the
`.env.development` / local seed, never in a deployed environment.

*Open decision:* confirm this approach before build.

## Requirements

### R1 — Staff profile

Fields:

- **Login link:** optional `platform_user_id`, so a staff member who has a console login maps to
  their own pipeline rows.
- **Basic:** full name, date of birth, gender, mobile, personal email, blood group (optional),
  address, emergency contact (name, relation, number).
- **Employment:** employee code (auto, e.g. `NRVN-S001`), designation (from a list, see R2),
  department, date of joining, status (`ACTIVE` / `RELEASED`), reporting manager.
- **Qualification:** list of entries — degree or certificate, institution, year, grade.
- **Documents:** list of uploads with a type (photo, ID proof, address proof, certificate,
  offer letter, other). PDF, JPG, PNG; 5 MB each.
- **Profile photo:** one image, used on the ID card. Cropped to a square on upload.
- **Salary and bonus (ADMIN only):** current monthly salary; bonus entries (date, amount, reason).

A profile is never hard-deleted once it has lead history. Set status to `RELEASED` instead, so the
lead trail stays intact.

### R2 — Designations

A managed list (add, rename, deactivate). Seeded with: Sales Executive, Senior Sales Executive,
Sales Manager, Onboarding Executive, Support Executive, Admin. Deactivating a designation hides it
from new profiles but keeps it on existing ones.

### R3 — Documents

- Upload, view, replace, remove (remove is a soft delete, flagged in the audit log).
- Documents are stored outside the database (object storage or the server's file store) with the
  profile ID in the path. They are served through an authenticated endpoint, never a public URL.
- Both ADMIN and SUPPORT can view documents. Only ADMIN can delete them.

### R4 — ID card printing

- Printable card from the profile: company logo, profile photo, name, employee code, designation,
  mobile, valid-until date (joining + 1 year, editable by ADMIN).
- Output: print-ready HTML to the browser print dialog, and a PDF export. Card size: 85 × 54 mm
  (credit-card). Front and back (back: company address, support phone, a QR code of the profile
  code).
- **Salary and bonus never appear on any card.**
- Printing is an action that is logged (who printed, when, which profile) in the audit log.

### R5 — Visiting card printing

- Card per staff member: name, designation, mobile, company email, the company website. Standard
  size 90 × 55 mm, front and back.
- Layout reuses the ID card components; no visiting-card data is pulled from salary or documents.
- Logged the same way as R4.

### R6 — Salary and bonuses (ADMIN only)

- Visible only to `PLATFORM_ADMIN`. Enforced by the **server**: the staff API returns the salary
  and bonus fields only to that role. The UI hiding them is not a control on its own.
- The SUPPORT role's staff responses omit the fields entirely, not as null or zero.
- Salary and bonus changes are recorded in the audit log with old and new values.
- Print templates for ID and visiting cards must not reference these fields.

### R7 — Lead generated by and closed by

"Lead" here means a row in the **sales pipeline** (`sales_lead`, the company's board of clinics being
sold to). It does **not** mean the contact-us enquiry (`lead`), which is clinic-facing claim data.

Every sales lead gets two optional references to a staff profile:

- **Generated by:** the person who found or brought in the lead (for example, who made the call
  that produced the enquiry, or who entered a lead from a referral).
- **Closed by:** the person who took the lead to a signed clinic.

Rules:

1. Both are set by ADMIN, or by a sales user entering a lead themselves. Generated by defaults to the
   user's linked staff profile (R1 login link) when they add a lead; without that link, it stays blank.
2. A lead counts as **closed** when it reaches the `LIVE` kind (milestone-based, never by stage name).
   Setting it sets **closed by**, the close date and the clinic it became. A lead can be closed
   by a different person from the one who generated it.
3. Changing either field is audit-logged.
4. The pipeline board and the lead dialog gain generated-by and closed-by fields and filters.
   Cold-pool leads keep no generator until a sales user first claims them (see open decision 3).

### R8 — Lead credit reports

A report of leads generated and closed per staff member over a date range:

- Counts: generated, closed, conversion rate (closed ÷ generated), in the range.
- Clinics closed (names and status, which the clinic list already has).
- Export to CSV.

This report shows **counts only**. It does not show salary, bonus or any amount tied to a person.
It is open to ADMIN and SUPPORT. Only ADMIN can see who was paid what.

### R9 — Audit log

An append-only table: who, what, which record, old and new value (where relevant), time. It
records: profile create/edit, salary or bonus change, document upload or removal, card print,
lead owner change, lead close.

## Data model (sketch)

- `staff_profile` (id, code, name, dob, gender, mobile, email, address, emergency fields,
  designation_id, department, joined_on, status, manager_id, photo_path)
- `staff_qualification` (id, staff_id, title, institution, year, grade)
- `staff_document` (id, staff_id, type, file_path, mime, size, uploaded_by, uploaded_at, deleted_at)
- `staff_salary` (staff_id, monthly_amount, effective_from, set_by) — ADMIN only read
- `staff_bonus` (id, staff_id, amount, bonus_date, reason, set_by) — ADMIN only read
- `staff_designation` (id, name, active)
- `sales_lead` gets `generated_by_staff_id`, `closed_by_staff_id`, `closed_on` (nullable; additive)
- `staff_profile.platform_user_id` (nullable, unique)
- `audit_log` (id, actor, action, entity, entity_id, old_value, new_value, at)

## Security and privacy

1. Salary and bonus tables are read only through an ADMIN-only query path. Test that a SUPPORT
   token gets no salary keys in any staff endpoint response.
2. No staff document or photo is publicly reachable.
3. Card printing (R4, R5) is ADMIN only, consistent with the roles table. SUPPORT may not print;
   see open decision 2.
4. The company data here must not leak into clinic-facing APIs or responses.
5. Every new write goes through `CurrentPlatformUserService.assertCanWrite()`, so `PLATFORM_SUPPORT`
   stays read-only on the server. The UI disabling a control is a courtesy only.

## Risks

- **Salary visibility bug.** A single missed serializer exposes pay to SUPPORT. Mitigation: the
  restricted fields live in a separate DTO that the list endpoint does not return.
- **Default credentials.** Mitigated by the one-time password above; reviewed before release.
- **Document storage cost and backup.** Keep uploads under 5 MB; include the store in backups.
- **Lead credit disputes.** Audit log and close date make changes traceable; no retroactive edits
  without a log entry.

## Build order

1. Schema and staff profile CRUD, designations, audit log.
2. ADMIN-only salary and bonus path, with tests for the SUPPORT response.
3. Documents and profile photo.
4. Sales-lead owner fields, pipeline board columns and filters, close flow.
5. ID card and visiting card print (HTML + PDF), logged.
6. Lead credit report and CSV export.
7. Seed the ADMIN login per the one-time-password rule.

## Open decisions

1. The `admin/admin` login: confirm the one-time password approach instead of a fixed password.
2. Should SUPPORT be able to print ID cards? (This PRD says no.)
3. Who sets a sales lead's **generated by** when it came from the cold pool (`sales_cold_lead`)
   or the marketing site: default to nobody, or to the first sales user who claims it?
4. Card validity: is one year from joining correct?
5. Aadhaar and PAN: confirm that no number is stored, only uploaded files.

## Decisions taken (10 Nov 2026)

1. `admin` login uses the one-time password approach (random, printed once or set from `DEVPORTAL_ADMIN_INITIAL_PASSWORD`, must change at first login). No fixed `admin/admin` in any deployed environment.
2. SUPPORT cannot print ID or visiting cards.
3. Cold-pool and marketing-site leads have no generated-by until a sales user claims them.
4. Card validity is one year from joining, editable by ADMIN.
5. No Aadhaar or PAN number is stored. Only uploaded files.
6. Sales role: `PLATFORM_SALES` does not exist in `health` (the `PlatformRole` enum has only `PLATFORM_ADMIN` and `PLATFORM_SUPPORT`). Lead credit is recorded and reported by ADMIN and SUPPORT only, so the sales column in the roles table is removed.

Note: `health`'s `PlatformDevDataSeeder` seeds a hardcoded `dev`/`dev` PLATFORM_ADMIN on every boot while `APP_PLATFORM_SEED_TESTING_LOGIN` is not false. It must be turned off before real data lives on the server.
